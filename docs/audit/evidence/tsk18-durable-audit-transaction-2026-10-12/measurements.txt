## Why `createdAtEqualsEventTimestamp` reads 0 in a naive re-run

The first pass of this instrument compared `"createdAt"` (returned by `node-postgres` as a JS `Date`
built from a `timestamp` **without time zone**) with the payload's `…Z` instant, and every row
mismatched by exactly the machine's UTC offset. The query now renders `createdAt` with
`to_char(…, 'YYYY-MM-DD"T"HH24:MI:SS.MS"Z"')` and compares text: **34 of 34**. The 0 was an
instrument bug, not a code bug, and it is recorded here rather than quietly re-run.

## Environment discovery: why `source .env` before `pnpm test` fabricates failures (2026-10-13)

Measured with a throw-away probe file (created, run, deleted — never committed):

```
NODE_ENV="development"  AUTH_BYPASS_ENABLED=undefined
resolveSessionUser({ headers: { "x-test-role": "SuperAdmin" } })  ->  null
POST /api/v1/workspace/content/CNT-LAGOS-201/publish  ->  401 {"code":"AUTH_TOKEN_REQUIRED"}
```

`.env` sets `NODE_ENV=development`. `(set -a; source .env; set +a; pnpm test)` puts that value in the
shell before Vitest starts, and Vitest only defaults `NODE_ENV` to `test` when it is *unset*. From
there the failure is mechanical: the test-role harness at `src/api/router.ts:730` is gated on
`process.env.NODE_ENV === "test"`, so `resolveSessionUser` returns `null` and every route that the
suite authenticates with `x-test-role` answers 401 (or 302 on the HTML paths). The first gates run on
the restored cluster was done that way and produced **6 spurious failures** — three in
`SEC-08: mutation idempotency (route level)` and three in `SCR-03`. Passing `DATABASE_URL` on the
command line instead (`DATABASE_URL=… pnpm test`) reaches the right database without touching
`NODE_ENV`, because `dotenv.config()` (`src/core/config/index.ts:5`) is called without `override` and
therefore cannot replace a variable the shell already set. Re-run that way: 106/106 in the two
affected files, 819/819 in the full suite.

Rule 0.3 says a gate may not be weakened to pass. Here nothing in the tree changed between the red
and green runs — only the environment, which is why both runs are filed in this directory.

## The golden seed and the count-asserting repository suites do not coexist (2026-10-13)

`pnpm db:seed` writes 5 VERIFIED talent, 11 ACTIVE campaigns, 50 programmes / 200 episodes into
`vmnl_enterprise` (the run itself is `db-seed-fresh-database.txt`). Three suites then assert the size
of a table they only ever add one row to — `tests/unit/production-core-and-infrastructure.test.ts:129`
(`listTalent({ tier: "VERIFIED" })` → 1), `:164` (`listCampaigns("ACTIVE")` → 1), `:213`
(`listAsRunRecords("NXTR")` → 1) — and `tests/unit/todo-final-remediation.test.ts:1829` asserts the
episode-master index at `{ channels: 3, programmes: 2, episodes: 3 }` while
`ensureScheduleDemoSeed()` (`:2207`) expects the seed to *refuse* to approve a day it cannot clear.
On the seeded database those seven assertions report 6 / 11 / 4 / 52 / 203 / 3-uncleared and the full
suite exits 10-red (`full-suite-golden-seeded-dev-db.txt`); on a migrated, unseeded database the same
tree is 819/819 green (`full-suite.txt`).

Consequence, stated rather than papered over: the DB-backed suites are only repeatable against a
database that holds **fixture rows**, not demo content. This run used a second, additive database
(`vmnl_enterprise_gates`) rather than deleting the seed rows from `vmnl_enterprise`, so the demo data
is still there for browsing the pages. Whether the suites should scope their count assertions
themselves is a register item, not something this evidence file will pretend is already fixed.

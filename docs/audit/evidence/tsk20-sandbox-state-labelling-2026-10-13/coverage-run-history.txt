Honest statement of what this leaves open
-----------------------------------------

The gate is **not deterministically green on this machine in this state**. It is
green twice (01:54 and 10:52) and red twice (09:56 and 10:25) on an unchanged
tree, with the red runs carrying the same route-probe timeout. The cause was not
established by these four runs — the load correlation is suggestive, not proof,
and no route was named because the message did not exist yet. What is *not* the
explanation: a weakened assertion, a skipped test, or a database difference — all
four runs used `postgresql://localhost:5432/vmnl_enterprise_gates`, migrated and
unseeded.

The follow-up this opens (recorded in `tasks.md`, not closed here): re-run with
the naming message until either a green run under high load or a red run under
low load appears, which decides whether the 10 s probe timeout is an environment
assumption or a route that really stalls. This record does not raise the timeout,
because that would be tuning the gate rather than measuring it.

The one-row-per-run residue is pre-existing behaviour of the privacy suite, not something this tree
introduced, and it is stated exactly because an earlier draft of this file had it wrong.
`tests/security/route-authorization.test.ts:277` POSTs `/api/v1/privacy/export-request`, and
`src/api/routes/privacy.routes.ts:64-71` deliberately persists a `DSR-EXP-<uuid>` ledger row for it
— the test asserts that write at `:289` — and nothing deletes it afterwards. Two traps produced the
wrong first reading: (a) those rows' `timestamp without time zone` values are written UTC-naive by
Prisma while the server session is `Africa/Lagos`, so a run at 01:36 local records 00:36 and one at
02:04 records 01:04; filtering on local wall clock therefore reports zero new rows. (b) Concluding
from that filter that the runs "tore down clean". They do not: pass A added 2 rows (00:36, 00:43
stored = 01:36, 01:43 local) and pass B added 2 (01:04, 01:07 stored = 02:04, 02:06 local). No
cleanup was attempted —
deleting ledger rows that the durability tests assert against would weaken a different gate, and the
suite is required (TSK-17) to be repeatable on this residue, which four 872/872 runs here confirm.
